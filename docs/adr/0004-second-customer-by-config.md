# ADR-0004: A second customer is a YAML file, and identity comes from the customer's proxy

Status: Accepted
Date: Phase 4

## Context

Harlow & Pryce (legal, 15 CUAD clause types, HubSpot + Slack) was the first customer.
The question every forward-deployed engagement eventually faces is whether the thing
built for customer one is a product or a bespoke script. We tested that by onboarding a
second customer in a different regulated domain with different clauses, different
integrations, and a different approval model:

**Meridian Health Partners** reviews HIPAA Business Associate Agreements (BAAs). The
eight required BAA elements (45 CFR 164.504(e)) replace the 15 commercial clauses; there
is no CRM and no Slack; the app must run fully offline; approvals must carry an
authenticated identity, not a typed name.

## Decision

1. **Clause types are data, not code paths.** The eight `baa_*` clause types were added to
   the shared `CLAUSE_TYPES` registry with keywords and a plain-English "why it matters".
   `customers/meridian-health.yaml` selects them. No reviewer, retrieval, app, MCP, or
   outbox code changed to support the second customer.

2. **Eval cases are partitioned by customer, and the gate tracks one customer.**
   `ccr-eval --customer <id>` scores only the clause types that customer checks and writes
   `docs/scorecard-<id>.svg`. The CI regression gate stays pinned to `harlow-pryce`, because
   mixing a 16-case hand-annotated set into a 120-case CUAD-derived gate would let a
   healthcare change mask a legal regression (or the reverse). `--update-gate` refuses to
   run with a non-default `--customer`.

3. **BAA eval cases are hand-annotated from anchors, not offsets.** CUAD has no BAAs. The
   16 healthcare cases are generated by `scripts/build_baa_evals.py` from exact sentences
   in two contracts: a complete BAA modelled on the HHS sample provisions, and a
   realistic vendor "data protection addendum" that is missing five of the eight required
   elements. Offsets are computed at build time, so the cases cannot drift from the text.
   The deficient addendum is the important half: it is what compliance officers actually
   catch, and it is where a keyword reviewer invents clauses that are not there.

4. **Approver identity is delegated to the customer's SSO proxy.** In `proxy_header` mode
   the app reads the authenticated user from a header (`X-Forwarded-User` by default) that
   oauth2-proxy, Cloudflare Access, or an ALB with OIDC injects after stripping any
   client-supplied value. The typed name is ignored; a missing header is a 401. The app
   does not validate tokens itself.

## Options considered

| Option | Why not |
|---|---|
| Fork the repo per customer | Two codebases within a month; every retrieval fix lands twice or once. This is the failure mode the engagement was meant to avoid. |
| Customer-specific subclasses of the reviewer | Clause lists and thresholds are the only real differences; a subclass hierarchy for data is over-engineering. |
| Merge all eval cases into one gate | A 16-case set moves the overall number by up to 12% on its own; the gate would stop meaning anything. |
| Implement OIDC in the app | Doing token validation, session handling, and key rotation inside a review tool duplicates what every customer already runs at the edge, and doing it badly is worse than not doing it. Delegating to the proxy also means the customer's IdP policy (MFA, device posture) applies without us knowing about it. |
| Keep the typed-name form in production | Audit trails that can be forged by typing a partner's name are not audit trails. |

## Consequences

- Onboarding Meridian took: 8 clause definitions, 1 YAML file, 2 sample contracts, 1
  annotation script. Zero changes under `src/reviewer/` other than the identity module.
- Healthcare scorecard on the hybrid engine with no tuning: 94% presence accuracy, 73%
  span recall, **0% hallucinated presence** on the deficient addendum. The keyword baseline
  hallucinates 60% on the same set. One honest miss: the vendor addendum's weak breach
  clause ("confirmed unauthorized access ... as soon as reasonably practicable") scores
  below the presence bar, so the reviewer refuses on it. A compliance officer would flag
  that clause as inadequate rather than absent; the two are different findings and the
  next iteration should distinguish "present but deficient".
- Every customer now has its own `docs/scorecard-<id>.svg`; the README shows both.
- The `Identity` block in `access:` is the first customer-config field that changes
  security behaviour. It is deliberately overridable by `CCR_IDENTITY_MODE` so the same
  image runs with the form in a pilot and behind the proxy in production.

## Revisit when

- A third customer needs a clause type with structure the `Finding` model cannot carry
  (e.g. a numeric limit that must be compared to policy). That is when clause definitions
  stop being data.
- A customer needs per-role identity inside MCP (not just HTTP). The MCP servers still
  read the role from `CCR_MCP_ROLE`; the plan is to have the proxy pass it as well.
